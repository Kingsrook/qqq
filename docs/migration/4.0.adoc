= Migrating to QQQ 4.0
:toc: left
:toclevels: 3
:source-highlighter: coderay
:icons: font

This guide covers every breaking change in QQQ 4.0.0 and provides step-by-step instructions for
migrating existing applications. Changes are grouped into four categories; each category includes
at least one concrete before/after example.

== Javalin import updates (BREAK-01) [[javalin-imports]]

The `qqq-middleware-javalin` module's root package changed from `com.kingsrook.qqq.backend.javalin`
to `com.kingsrook.qqq.middleware.javalin`. Apply this rename to every import statement that
references the old package.

=== What changed

[cols="1,1", options="header"]
|===
|Old import (0.x)
|New import (4.0)

|`com.kingsrook.qqq.backend.javalin.QJavalinImplementation`
|`com.kingsrook.qqq.middleware.javalin.QJavalinImplementation`

|`com.kingsrook.qqq.backend.javalin.QJavalinMetaData`
|`com.kingsrook.qqq.middleware.javalin.QJavalinMetaData`

|`com.kingsrook.qqq.backend.javalin.QJavalinProcessHandler`
|`com.kingsrook.qqq.middleware.javalin.QJavalinProcessHandler`

|`com.kingsrook.qqq.backend.javalin.QJavalinScriptsHandler`
|`com.kingsrook.qqq.middleware.javalin.QJavalinScriptsHandler`

|`com.kingsrook.qqq.backend.javalin.QJavalinAccessLogger`
|`com.kingsrook.qqq.middleware.javalin.QJavalinAccessLogger`

|`com.kingsrook.qqq.backend.javalin.QJavalinUtils`
|`com.kingsrook.qqq.middleware.javalin.QJavalinUtils`

|`com.kingsrook.qqq.backend.javalin.*` (any class)
|`com.kingsrook.qqq.middleware.javalin.*`
|===

=== Migration example

[source,java]
.Before (0.x)
----
import com.kingsrook.qqq.backend.javalin.QJavalinImplementation;
import com.kingsrook.qqq.backend.javalin.QJavalinMetaData;
import com.kingsrook.qqq.backend.javalin.QJavalinProcessHandler;
----

[source,java]
.After (4.0)
----
import com.kingsrook.qqq.middleware.javalin.QJavalinImplementation;
import com.kingsrook.qqq.middleware.javalin.QJavalinMetaData;
import com.kingsrook.qqq.middleware.javalin.QJavalinProcessHandler;
----

=== How to update

Use a bulk find-and-replace across your project source tree:

[source,bash]
----
# In your project root
find . -name "*.java" ! -path "*/target/*" \
  -exec sed -i 's/com\.kingsrook\.qqq\.backend\.javalin/com.kingsrook.qqq.middleware.javalin/g' {} +
----

Verify no residuals remain:

[source,bash]
----
grep -r 'com\.kingsrook\.qqq\.backend\.javalin' . --include='*.java' --exclude-dir=target
# Expected: no output
----

== Removed @Deprecated APIs (BREAK-03) [[removed-deprecated-apis]]

All elements annotated `@Deprecated` on the public surface of every published module were removed
in 4.0.0. The items below are grouped by the module and commit they were removed from.

[NOTE]
====
If your code fails to compile with `cannot find symbol` errors after upgrading, check this section
first. Every removed element has a direct replacement.
====

=== BREAK-03-A: QBackendMetaData variantOptionsTable accessors removed

22 deprecated elements removed from `QBackendMetaData` in `qqq-backend-core`:
2 private fields (`variantOptionsTableTypeField`, `variantOptionsTableTypeValue`),
20 deprecated `variantOptionsTable*` accessors,
and the `LegacyBackendVariantSetting` companion enum.

[source,java]
.Before (0.x) — using deprecated variantOptionsTable accessors
----
metaData.setVariantOptionsTableName("myTable");
metaData.setVariantOptionsTableIdField("id");
metaData.setVariantOptionsTableTypeField("type");
----

[source,java]
.After (4.0) — use the non-deprecated replacement accessors
----
// The non-deprecated getters/setters for variant options remain on QBackendMetaData.
// Remove any calls to the deprecated variantOptionsTable* overloads.
// Use APIBackendVariantSetting directly instead of LegacyBackendVariantSetting.
----

=== BREAK-03-B: Miscellaneous zero-caller deprecated elements removed

Removed from 5 files in `qqq-backend-core` and `qqq-middleware-api`:

[cols="2,1,2", options="header"]
|===
|Removed element
|Module
|Replacement

|`ExtractViaQueryStep.customizeInputPreQuery(QueryInput)` 1-arg
|qqq-backend-core
|Use the 2-arg overload with `Consumer<QueryInput>` callback

|`QRecordListMetaData.addField(QFieldMetaData)`
|qqq-backend-core
|Use `withField(field)` fluent builder

|`QRecordEntity.toQRecordOnlyChangedFields()` 0-arg
|qqq-backend-core
|Use `toQRecordOnlyChangedFields(false)`

|`BaseAPIActionUtil.setSession(QSession)`
|qqq-middleware-api
|Remove call — unused setter

|`ApiFieldCustomValueMapper.customizeFilterCriteria(QueryInput...)` vararg
|qqq-middleware-api
|Override `customizeFilterCriteriaForQueryOrCount` — now no-op by default
|===

[source,java]
.Before (0.x)
----
entity.toQRecordOnlyChangedFields();
----

[source,java]
.After (4.0)
----
entity.toQRecordOnlyChangedFields(false);
----

=== BREAK-03-C: qqq-openapi String-typed setIn/withIn/setType/withType type-narrowed

`Parameter.setIn(String)` / `withIn(String)` and `Schema.setType(String)` / `withType(String)`
overloads that accepted free-form `String` arguments were removed.
Use the `Parameter.In` and `Schema.Type` enum-typed overloads.

[source,java]
.Before (0.x)
----
parameter.setIn("query");
schema.setType("string");
----

[source,java]
.After (4.0)
----
parameter.setIn(Parameter.In.QUERY);
schema.setType(Schema.Type.STRING);
----


== API-shape cleanups (BREAK-04) [[api-shape-cleanups]]

These are targeted API-shape changes where the replacement has a different method signature,
type parameter, or class hierarchy. Each item is identified by its BREAK-04-NN ID from the backlog.

=== BREAK-04-01: qqq-bom now manages 5 additional modules

*Module:* `qqq-bom`

The following 5 modules were not previously managed by `qqq-bom`. They are now included.
If you had explicit version pins for these modules in your `pom.xml`, remove them.

[source,xml]
.Newly managed by qqq-bom (4.0)
----
qqq-backend-module-sqlite
qqq-backend-module-postgres
qqq-middleware-lambda
qqq-middleware-health
qqq-utility-lambdas
----

=== BREAK-04-02: qqq-utility-lambdas promoted to Java 21

*Module:* `qqq-utility-lambdas`

The module now targets Java 21 bytecode (previously Java 11). If your project targets Java 11
or 17, you cannot use `qqq-utility-lambdas`. Upgrade to Java 21.

=== BREAK-04-03: qqq-middleware-javalin annotation-processor block retained at Java 11

*Module:* `qqq-middleware-javalin`

The annotation-processor compiler block that generates OpenAPI bytecode is intentionally
retained at Java 11. The Java 21 JDK can legally produce Java 11 class files. No action required.

=== BREAK-04-04: Qodana static analysis aligned to JDK 21

*File:* `.qodana.yml` (or `qodana.yml`)

[source,yaml]
.Before
----
projectJDK: 17
----

[source,yaml]
.After
----
projectJDK: 21
----

=== BREAK-04-06: JsonUtils deprecated 2-arg toJson removed

*Location:* `qqq-backend-core` — `JsonUtils.toJson(Object, Consumer<ObjectMapper>)`

[source,java]
.Before (0.x)
----
String json = JsonUtils.toJson(myObject,
   mapper -> mapper.disable(SerializationFeature.INDENT_OUTPUT));
----

[source,java]
.After (4.0) — use toJsonCustomized for builder-level config
----
String json = JsonUtils.toJsonCustomized(myObject,
   builder -> builder.disable(SerializationFeature.INDENT_OUTPUT));
----

Or use `toJsonWithMapper` when you need post-build mapper access:

[source,java]
.After (4.0) — use toJsonWithMapper for post-build mapper config
----
String json = JsonUtils.toJsonWithMapper(myObject,
   mapper -> mapper.setSerializerProvider(customProvider));
----

=== Deferred items (not in 4.0.0)

The following item from the original BREAK-04 backlog was deferred by Phase 4 and will be
addressed in a future 4.x release:

* *BREAK-04-05*: AWS SDK v1 and v2 consolidation — mixed SDK usage (`software.amazon.awssdk` and
  `com.amazonaws`) remains in the RDBMS and S3 filesystem modules. No action required for 4.0
  migration; consolidation tracked for a future release.
